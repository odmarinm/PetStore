PETSTORE API AUTOMATION - CONCLUSIONS
=====================================

Repository: https://github.com/odmarinm/PetStore (public)
API under test: https://petstore.swagger.io/v2 (public Swagger PetStore, shared server)


1. SUMMARY
----------
An API test automation project was built for the "user" resource of the Swagger PetStore.
It covers the full life cycle of a user: create, query, update and delete.

Current suite: 3 features, 7 scenarios, 38 steps - all passing.
The project was verified from a clean clone following only the README instructions.


2. TECHNOLOGIES
---------------
- Python 3.11+ (developed and tested with Python 3.15)
- Behave 1.3.3 ............ BDD framework, scenarios written in Gherkin
- requests 2.34.2 ......... HTTP client
- jsonschema 4.26.0 ....... response validation against JSON Schemas
- python-dotenv 1.2.4 ..... configuration from a .env file
- allure-behave 2.16.2 .... Allure results generated by Behave
- Allure CLI 2.x + Java ... HTML report (optional: tests run without it)
- Git + GitHub ............ version control

Why Python + Behave instead of Karate
-------------------------------------
Karate was the desired or suggested tool for this project, but Python + Behave was chosen
because it fit the project's needs better:

- Readable scenarios: in Karate the .feature holds URLs, JSON and "match" expressions; with
  Behave it only describes behavior and the technical details stay in Python.
- Custom logic as plain code: per-field Allure sub-steps, reporting all errors together,
  password masking and GET retries are simple Python; in Karate they need embedded JS/Java.
- Reusable layers: builders, interactors, requests and validators are shared across features
  and easy to extend to new resources (pet, store).
- Native Allure report (allure-behave) with sub-steps and request/response attachments.
- Lighter runtime: only Python, no JVM/Maven/Gradle (Java only to open the Allure HTML).
- Follows the reference architecture used as the model (Python + Behave + Allure).

Trade-off: Karate needs less code for simple checks (built-in HTTP, JSON "match", parallel
runner, mocks); Behave needs more initial code, but it is reusable and gives full control.


3. ARCHITECTURE
---------------
Layer rule: features -> steps -> interactors -> requests. Only src/requests makes HTTP calls.

  features/      Gherkin .feature files, grouped by resource (features/user/)
  steps/         Given builds data, When sends the request and stores the response, Then validates
  builders/      Build payloads (UserBuilder); never make HTTP calls
  interactors/   Use cases called by the steps (UserInteractor)
  requests/      BaseClient + UserRequests: the only layer that talks to the API
  validators/    Response validations, no HTTP
  schemas/       JSON Schemas: User and ApiResponse
  config/        Settings loaded from .env (BASE_URL, API_KEY, REQUEST_TIMEOUT)
  enums/         Endpoint, ContentType, ApiResponseType

Design decisions:
- ONE consolidated validation step per operation ("the creation/update/deletion of the user
  has been successful"), instead of many small "field X should match" steps.
- Code is reused across features: the create steps are the precondition of the update and
  delete features, and the three operations share the same ApiResponse validation.
- Test data is unique per run (random username and id) because the server is shared.


4. ENDPOINTS VALIDATED
----------------------
  Method  Endpoint               Feature              Tag
  ------  ---------------------  -------------------  ------------
  POST    /user                  create_user.feature  @create_user
  PUT     /user/{username}       update_user.feature  @update_user
  DELETE  /user/{username}       delete_user.feature  @delete_user
  GET     /user/{username}       used by all three to confirm the result

All features also have the @user tag (runs the whole user suite).


5. SCENARIOS
------------
create_user.feature
  - Create a user with all fields (2 examples: Ana Lopez, Carlos Perez)
  - Create a user with only the username

update_user.feature
  - Create a user, look it up with GET, change first name and email, send it with PUT
    (2 examples: Ana -> Maria, Carlos -> Andres; the last name does not change)

delete_user.feature
  - Create a user, delete it with DELETE, then confirm it no longer exists
    (2 examples: Ana Lopez, Carlos Perez)


6. VALIDATIONS PERFORMED
------------------------
Every comparison uses assert_equals (src/utils/assertions.py).

a) Status code of the operation: 200.

b) ApiResponse of POST / PUT / DELETE:
   - Content-Type is application/json
   - Body matches the ApiResponse JSON Schema (code, type, message; no extra fields)
   - code = 200
   - type = "unknown"
   - message = the user id (POST and PUT) or the username (DELETE)
   - When no id is sent, message must be a numeric id

c) Create and update - saved user (GET /user/{username}):
   - GET returns 200
   - Body matches the User JSON Schema
   - Field by field, what was SENT in the request equals what GET RETURNS:
     id, username, firstName, lastName, email, password, phone, userStatus
   - In the update, the unchanged fields must keep their values
   - Fields that were not sent have the expected default (missing, or userStatus = 0)
   - When no id is sent, the saved id must equal the message of the POST

d) Delete - the user no longer exists (GET /user/{username}):
   - Status code = 404
   - Body matches the ApiResponse JSON Schema
   - code = 1, type = "error", message = "User not found"

Errors are not stopped at the first failure: all checks run and a single error lists
every field that failed.


7. ALLURE REPORT FORMAT
-----------------------
- Each scenario shows its Gherkin steps.
- Every HTTP call is a step "<METHOD> <URL>" with two attachments:
  "Request body" (JSON) and "Response <status code>" (JSON).
- The validation step contains groups, for example:
    Validate POST /user (ApiResponse)
    Validate saved user (GET /user/{username})
    Validate user no longer exists (GET /user/{username})
- Inside each group, one sub-step per check, with the expected and actual values:
    ✔ firstName: expected 'Ana' | got 'Ana'
    ✘ email: expected 'a@x.com' | got 'b@x.com'      (red when it fails)
  A group turns red if any of its checks fails.
- The password is masked ('***') in the report.
- GET retries are shown as steps, e.g. "Retry 2/5: user not available yet".
- The "Environment" widget shows Base URL, Python version and operating system.
- reports/allure-results is cleared at the start of each run, and the HTML report
  (reports/allure-report) is regenerated automatically at the end, so it always shows
  the latest execution. Open it with: allure open reports/allure-report
- All report and error messages are in English.


8. IMPORTANT FINDINGS (REAL API vs SWAGGER)
-------------------------------------------
- POST and PUT do not return the user, only an ApiResponse
  {"code":200,"type":"unknown","message":"<id>"}. That is why GET is used to validate.
- DELETE returns the same ApiResponse, but message is the USERNAME, not the id.
- Swagger does not document the 200 response of PUT and DELETE (only 400 and 404).
- Swagger says PUT and DELETE require a logged-in user; the real API does not.
- PUT requires the FULL User object. A partial body (only the changed fields) returns 200
  with message "0" but updates nothing. That is why the update first reads the user.
- PUT on a user that does not exist returns 200, not 404 as Swagger says.
- DELETE on a user that does not exist returns 404 with an empty body.
- GET on a deleted or missing user returns 404 with
  {"code":1,"type":"error","message":"User not found"}.
- Without an explicit id, the server may assign an invalid one (~9223372036854...), so the
  tests send their own id.
- The server runs several instances behind a load balancer: a new or deleted user can take
  a moment to be visible. GET is retried (up to 5 times, 1 s apart) while the user is not
  found yet (create/update) or is still found (delete).


9. RELIABILITY
--------------
- The HTTP client retries connection errors (e.g. transient DNS failures) up to 5 times,
  waiting 0, 2, 4, 8 and 16 s. Only failed connections are retried: the request never
  reached the server, so POST/PUT are not duplicated. HTTP errors are NOT retried, so real
  API failures are never hidden.
- A failure with "NameResolutionError" means a network problem, not a test failure.
- Usernames are random so parallel or repeated runs do not collide on the shared server.


10. HOW TO RUN (short version - see README.txt for details)
----------------------------------------------------------
  git clone https://github.com/odmarinm/PetStore.git
  cd PetStore
  python -m venv .venv
  .\.venv\Scripts\pip install -r requirements.txt      (macOS/Linux: .venv/bin/pip ...)
  copy .env.example .env                                (macOS/Linux: cp ...)
  .\.venv\Scripts\behave                                (or --tags=@update_user, etc.)
  allure open reports/allure-report
